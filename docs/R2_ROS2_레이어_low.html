ROS2는 어떻게 동작하나? (초보자 · 바이트 스트림)

위 그림의 /scan, /map 같은 이름은 “네트워크에 날아다니는 문자열 명령”이 아닙니다. R2 안에서는 여러 층의 데이터 길이 있고, 층마다 실리는 바이트 형식(프로토콜)이 다릅니다.

한 줄 요약

하드웨어(시리얼/USB)에서는 헤더·길이·명령·데이터·체크섬 같은 바이너리 프레임을 파싱하고, 그 결과를 ROS2 메시지 객체로 바꾼 뒤, 노드끼리 통신할 때는 DDS가 그 메시지를 다시 바이트로 직렬화해 보냅니다. ROS2 토픽 이름 자체가 “예약어 키워드 프로토콜”은 아닙니다.

1) 층으로 보기 — 어디서 바이트가 흐르나

아래는 같은 네 층을 등각(isometric) 3D 육면체 탑으로 그린 것입니다. 맨 아래(노랑)가 전선 위의 날바이트, 맨 위(초록)가 노드끼리 다시 네트워크로 보내는 층입니다. 데이터가 위로 갈수록 “의미 있는 메시지”가 되고, 꼭대기에서 다시 바이트로 포장됩니다.

그림 · R2 데이터 계층 (3D 육면체 스택)

바닥 = 하드웨어 전선  ·  꼭대기 = ROS2 노드 간 전송 (DDS)

물리 배선(STM32·USB HUB·Jetson)은 R2_HW_배선.html 문서에 정리되어 있습니다.

그림 · 누가 누구에게 보내나 (소프트웨어 · ①~④)

왼쪽 하드웨어 입력은 경로가 갈라진 뒤 · 큰 박스 안 = Jetson 프로세스

같은 내용을 글 카드로 풀어 쓴 것이 바로 아래 1→4 목록입니다. 그림의 색깔·번호와 맞춰 읽으면 됩니다.

1 하드웨어 선 (물리 바이트 스트림) UART · USB · /dev/myserial · /dev/ydlidar …

ROS 확장판(STM32) · USB HUB 확장판 · Jetson. 라이다/카메라는 매뉴얼상 USB HUB를 거쳐 Jetson으로. 전선 위에는 0과 1(바이트 나열)만 있습니다. R2 본체 제어는 보통 Rosmaster_Lib가 시리얼을 읽고 씁니다 (Ackman_driver_R2.py → set_car_motion / get_motion_data).

2 장치 드라이버 / SDK (프레임 파싱) Rosmaster_Lib · 라이다 드라이버 · Orbbec/Astra 드라이버

“이 바이트 줄이 한 프레임의 시작인가?”를 보고 동기 헤더 → 길이 → 기능코드/명령 → 페이로드 → 체크섬을 잘라 숫자·구조체로 만듭니다. 여기까지는 아직 ROS2가 아닙니다.

3 ROS2 노드 · 토픽 · 메시지 (의미 있는 데이터) publisher / subscriber · .msg 타입

파싱된 값을 sensor_msgs/LaserScan, nav_msgs/Odometry, geometry_msgs/Twist 같은 정해진 필드 구조에 넣어 토픽 이름(예: /scan, /cmd_vel)으로 주고받습니다. 토픽 이름은 주소 라벨에 가깝고, HTTP의 GET 같은 예약 키워드 체계가 아닙니다.

4 노드 간 전송 (다시 바이트로) DDS / RTPS · CDR 직렬화 · UDP 등

같은 컴퓨터(또는 같은 ROS_DOMAIN_ID 네트워크)의 다른 노드가 받으려면, ROS2가 메시지를 CDR로 바이트 배열로 만들고 DDS(RTPS) 프로토콜로 실어 보냅니다. 사용자는 보통 이 층을 직접 파싱하지 않습니다 — create_subscription 콜백에 이미 복원된 메시지 객체가 들어옵니다.

Ackman_driver_R2.py는 /cmd_vel(Twist)을 구독 → Rosmaster_Lib.set_car_motion(vx, vy, angular)로 시리얼 바이트 전송 → 타이머로 보드에서 IMU·전압·속도 등을 읽어 /imu/data_raw, /vel_raw 등으로 다시 ROS2 메시지 발행합니다. 즉 “하드웨어 프로토콜 ↔ ROS2 메시지” 번역기입니다.

3) 하드웨어 쪽 바이트 프레임 — protocol 이 있나?

있습니다. 다만 ROS2 표준 문서에 있는 형식이 아니라, 보드·센서 제조사(Yahboom 확장보드, 라이다 벤더 등)가 정한 장치 전용 바이너리 프로토콜입니다. 공통 패턴은 아래와 같습니다 (임베디드 시리얼에서 매우 흔함).

① SYNC / 헤더 고정 바이트
예: 0xFF 0xFC …
② LENGTH 이 뒤 페이로드
몇 바이트인지
③ CMD / FUNC 무슨 명령?
속도·IMU·부저…
④ PAYLOAD (데이터) 실제 값들 (속도 float, 가속도, 전압…)
타입·순서는 제조사 표에 정의
⑤ CHECK checksum
깨진 프레임 버림

※ 위 숫자(0xFF 등)는 전형적인 형태 예시입니다. R2에서 쓰는 정확한 매직 넘버·체크섬 식은 출하 이미지의 Rosmaster_Lib(또는 하드웨어 매뉴얼)에 있습니다. 사용자 코드는 보통 그 라이브러리 API만 호출합니다.

수신 쪽 파싱 순서 (초보자용 의사코드)

# 시리얼에서 바이트가 끊임없이 들어올 때
while True:
    b = read_one_byte()
    if not in_frame:
        if matches_sync_header(b):   # ① 예약된 시작 바이트(들) 찾기
            in_frame = True
            buf = [b]
        continue
    buf.append(b)
    if len(buf) >= HEADER_SIZE:
        length = parse_length(buf)   # ② 길이 필드로 "이 프레임 끝" 계산
    if frame_complete(buf, length):
        if checksum_ok(buf):         # ⑤
            cmd = parse_cmd(buf)     # ③
            data = parse_payload(buf)# ④
            # → ROS2 메시지로 채워서 publish
        else:
            discard()                # 깨진 패킷
        reset_frame()

하드웨어 프로토콜에 “있는” 것

  • 프레임 시작을 알리는 고정 헤더(SYNC)
  • 길이(length) — 가변 길이 프레임일 때
  • 명령/기능 코드 — 어떤 종류의 데이터인지
  • 페이로드 + 체크섬/CRC
  • 보드·센서마다 표가 다름 (문서/라이브러리 필수)

ROS2 메시지 층에 “없는/다른” 것

  • 토픽 문자열을 바이트로 파싱하는 “키워드 프로토콜” 아님
  • 대신 .msg 스키마로 필드 이름·타입이 컴파일 타임에 정해짐
  • 와이어 포맷은 보통 CDR (필드 순서 고정 바이너리)
  • 전송 제어는 DDS/RTPS (GUID, 시퀀스 번호, QoS…)
  • 앱 개발자는 메시지 객체만 다룸

4) ROS2가 네트워크에 실을 때 (DDS 쪽, 개념만)

노드 A가 LaserScan을 publish 하면, 미들웨어가 대략 이렇게 바꿉니다.

이 프로젝트 스크립트는 ROS_DOMAIN_ID(예: 28)로 “같은 로봇 무리”만 서로 말 걸게 합니다. 도메인이 다르면 토픽 이름이 같아도 안 보입니다.

구성 요약
  • 물리: STM32 보드와 USB HUB 보드는 별도 PCB. 둘 사이 — 2핀 +/- 전원, USB(MCU 시리얼). 카메라·라이다 → HUB → Jetson. 소프트웨어 장치: /dev/ydlidar, /dev/AstraPlus, /dev/myserial (scripts/run_docker_env.sh 등).
  • STM32 시리얼: HUB 경유 USB-UART → Ackman_driver_R2.py → Rosmaster_Lib (라이브러리는 출하 이미지; 포트 오픈은 라이브러리 내부).
  • 라이다: laser_bringup_launch.py → ydlidar_ros2_driver / sllidar_ros2 (library_ws).
  • 카메라: laser_bringup에 포함되지 않음. ros2 launch astra_camera astro_pro_plus.launch.xml (scripts/start_camera.sh 등).
  • RTAB-Map 입력: rtabmap_sync_launch.py — /camera/color/image_raw, /camera/depth/image_raw, /odom, scan.
